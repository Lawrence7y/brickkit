## 2. 当前数据仍只能用于 smoke，不构成真实套装留出

### 2.1 750 个独立哈希主要来自顶部序号

生成器通过 `draw.text(..., f"#{sample_idx:04d}", ...)` 在状态图左上角写入全局样本编号。

独立检查结果：

| 对状态图的处理 | 不同内容数量 |
|---|---:|
| 原始 PNG | 750 |
| 去除顶部 24 像素的序号区域 | 8 |
| 同样去除序号并只保留前景轮廓 | 4 |

因此“字节去重为 0”可以成立，但不能据此声称几何结构已经覆盖 750 个独立装配状态。这些图仍由 4 种二维底座模板构成，没有从对应套装的真实装配关系渲染。

这属于数据设计问题；无需删除 smoke 样本，应继续保留其明确分类。

### 2.2 不看图像的训练集查表基线仍能全对

本次没有读取测试标签来形成预测规则，只在 train 中建立两个简单映射：

- 第一个候选的 `orientationId` → 正确候选位置：12 个键；
- 第一个候选的 `parentConnectorId` → 结构是否有错：3 个键。

随后直接在 holdout 上预测：

| 任务 | 结果 |
|---|---|
| 动作候选选择 | 150/150，100% |
| 结构错误分类 | 75/75，100% |
| 训练映射中互相冲突的标签 | 0 |

原因是动作答案、旋转编号、接口编号和结构标签共同来自相同循环变量的公式。正确动作不是由目标结构与当前结构的几何关系决定的。

所以 87.33% 可以记录为此 smoke 数据上的模型结果，但不能只与随机 25% 比较并认定已有领域理解收益。三个 family ID 的互斥也不能证明对三个真实套装泛化。

当前“候选覆盖率 100%”同样只证明脚本把自己选择的候选放进了列表，尚未评价 A 引擎枚举对真实装配正确动作的覆盖能力。

## 4. Qwen 的训练调用存在，图像数据仍未进入 Dataset 的 processor

当前 `QwenVLMDataset.__getitem__` 先调用 `apply_chat_template(..., tokenize=False)` 得到文本，再执行：

```python
inputs = self.proc(text=[text], padding=True, return_tensors="pt")
```

该路径未传实际图像或视频，也没有生成并检查 `pixel_values` / `image_grid_thw`。消息中的图片路径和文本中的图像占位符不等于图像像素张量。Qwen 官方接口明确区分这两类输入，参见 [Transformers Qwen2.5-VL 文档](https://huggingface.co/docs/transformers/model_doc/qwen2_5_vl)。

另外，labels 直接复制所有 input_ids，尚未实现所声明的 assistant-only 标签；没有显式多模态 collator，也没有单 batch forward/backward 的实际证据。`--dry_run` 当前在 Dataset/Trainer 构造之前返回，只验证样例对话，不能验证后面的多模态训练路径。

本次未下载基座或尝试高显存训练。准确状态应是：已有训练调用与预检，完整多模态训练入口未验证。资源不足可以保留该状态，不应再写成已经完整就绪。
