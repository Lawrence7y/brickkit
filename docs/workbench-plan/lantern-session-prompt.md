# 灯笼修复会话提示词

以下正文可直接复制给正在修灯笼的 Harness 主会话。

---

你继续负责 BrickKit 的实物灯笼修复。飞机／机甲暂缓。另一个 Harness 会在独立工作树开发乐高搭建工作台；你与它并行，但不共同修改共享文件。

## 目标与执行方式

目标是用现有六张实拍照片修复一个零件与连接可信、可复核、可导出说明书的灯笼模型。结构与接口正确优先于外观分数；外观、数量和颜色也要逐项对账。不要把测试通过、几何自洽或 diff 达标称为实物复拼通过。

你已获授权使用子代理与主会话并行。默认最多主会话加两个子代理；若运行环境更紧张则减少并发，不减少验收。先列出每个代理的文件所有权，再开工。所有代理都不是独自在仓库中，不得撤销、覆盖或清理其他人的修改，不得共同写同一个文件。主会话负责实施与结果整合，独立审计代理不能一边修改模型一边给自己验收。

先读工作区 `AGENTS.md`、`docs/workbench-plan/PRD.md`、`docs/workbench-plan/README.md`。主会话先用 `git status --short` 与相关 diff 建立当前基线，记录分支／提交及已存在的脏文件。不要用 reset、checkout、restore、clean 恢复任何不属于自己的修改。

## 先接续当前成果，不从头做

仓库在 2026-10-27 已存在下列候选，不代表它们已通过验收：

- `examples/gen-lantern-v3.mjs` 与 `examples/lantern.reconstructed.v3.brick.json`。
- `examples/gen-lantern-v4.mjs` 与 `examples/lantern.reconstructed.v4.brick.json`。
- `examples/lantern.observations.v2.json` 与 `examples/lantern.observations.v3.json`。
- 旧模型 `examples/lantern.reconstructed.brick.json` 与旧生成脚本。
- `out/lantern-v3/`、`out/lantern-v4/` 及已有对照、测量、报告目录。

先读取实际最新文件、脚本运行参数与已有报告，判断哪些能复用。版本号更大、输出更多或说明更肯定，均不代表更正确。不同观察记录已经出现互相推翻的结论，必须回到原照片。

尤其检查如下冲突，不预设答案：

1. 立柱是纯圆板、纯圆砖，还是圆砖与圆板混合？每柱节数是多少？
2. 底部绿色是中央单件还是多件十字？照片可见外形与隐藏分件应分开记录。
3. 淡紫顶板是平行并排、错位还是实际旋转？不要把透视斜线直接当成旋转角度。
4. 芯柱到底有多少颗，颜色段数是否等于零件数？不要用柱顶对齐反推一个数后把它称为照片确认。
5. 最新观察中，同一条“圆砖＋圆板”结论可能同时出现在 proven 与 pending；需要消除这种事实／推断混写。

## 并行分工

### 主会话：唯一模型实施者与集成负责人

- 负责续接基线、候选选择、builder 搭建、连接修复、最终模型和生成脚本。
- 写入域：新的 `examples/gen-lantern-<下一版本>.mjs`、对应 `.brick.json`、版本化照片／观察清单、`out/lantern-repair/<本轮唯一运行名>/main/`。
- 未经核对不要覆盖 v2/v3/v4 或正式旧模型；在报告里给出推荐候选与原因，成功后再明确是否提升为正式版本。
- 汇总两位子代理意见，逐条处理，必要时将新快照交回审计代理复验。

### 子代理 A：照片独立审计

- 只读模型、脚本与原始照片；先观察实物，再对比模型，不沿用 meta 中的自我评价。
- 写入域仅为 `out/lantern-repair/<本轮唯一运行名>/photo-audit/`。
- 输出观察表、模型差异、截图／裁剪索引、仍待确认事项和必要补拍建议。不得修改候选模型、目录、代码或其他代理报告。

### 子代理 B：连接独立审计

- 只读主会话指定的模型快照与现有核心。输出快照哈希，避免审计途中模型变化。
- 写入域仅为 `out/lantern-repair/<本轮唯一运行名>/connection-audit/`。
- 检查全部非基础件的真实连接接口、连通链、占用冲突、穿模、步骤顺序和支撑。引擎自动校验与照片／独立几何检查分别报告。
- 不得通过改容差、豁免、目录或测试预期让模型通过。发现核心缺口，写明最小复现与所需接口，不直接修改核心。

## 与编辑工作台会话的边界

你不修改 `src/core/**`、`src/viewer/**`、`catalog/**`、`cli/**`、`build.mjs`、`package*.json`、`test/**`、`dist/**` 与共享历史验收文档。不得重建生产目录或修改机甲模型。原有这些文件的脏修改不属于本任务，保持原样。

出现引擎能力缺口时，在本轮 `interface-requests.md` 中记录触发模型、当前结果、预期结果、证据、建议接口和阻塞范围。继续模型与证据工作，不以新增假件、任意浮点位移、扩大碰撞豁免代替核心修复。核心改动由明确的单一负责人单独整合。

编辑工作台仅加载一个冻结的灯笼快照作为样本，不读写你正在变化的候选。交付样本时一起给出模型、照片清单和相关目录的哈希／版本说明。用户在工作台里的编辑保存为草稿，不覆盖你的原模型。

## 搭建与核验

1. 优先用统一 `mergeCatalogParts` 读取目录，用 `createBuilder` 和真实接口搭建；核对真实编号，不猜编号、不手写 JSON 坐标。侧装遵守项目 SNOT 与 snap 规范。
2. 每个模块完成后运行静态校验，最终要求零 errors、零 warnings。无法达到时保持任务未完成并列明原因，不改预期绕过。
3. 对新照片清单运行 `check-photos`，如实记录 complete 与 skipped 的理由，不把已有“旋转对称”备注视为自动免检依据。
4. 初稿通过校验后，渲染 az=0/180/270/90、el=5 的四向正交图，并逐张与实物照片对照。照片不对应正交机位时记录局限，并补照片机位渲染，不能宣称存在没有拍到的独立视角。
5. 运行观察数量对账与 diff，要求 `overall.score >= 0.6`；保留逐张分数、掩膜 degraded 状态及比例／色块误差。分数与视觉冲突时优先核查掩膜和机位，不选择明显错误的结构去迎合分数。
6. 新导出写到本轮独立目录，生成 `.viewer.html`、A4 横版 `.booklet.pdf`、`.mpd`。实际打开查看器，检查旋转、模块爆炸、步骤切换；检查 PDF 页面是否缺件、裁切和漏步。导出命令若依赖重写共享 `dist`，不要运行共享构建：登记依赖，使用明确隔离的构建副本或现有可用构建，并记录其版本。不能把旧构建产物当成新构建成功。
7. 跑与本次模型变化相关的现有检查；核心／全库测试不在本会话修改范围。记录真实通过、失败和跳过数量。重复测试仅在新变化、失败或未解问题要求时进行。

## 交付

在 `out/lantern-repair/<本轮唯一运行名>/` 形成：

- `main/baseline.md`：接续了哪些文件、哈希、原有问题与候选选择理由。
- `main/connections.json`：每条连接的两件 ID、接口身份、配对类型和证据等级；推导不等于独立验证。
- 两位子代理的独立报告及主会话逐条处理结果。
- 四向正交图、照片机位对照、validate／observations／diff 报告。
- 新脚本／模型／照片清单／观察清单的索引及哈希。
- 查看器、图纸、MPD 和实际打开检查记录。
- `interface-requests.md`：没有核心缺口也明确写无。
- `result.md`：推荐候选、真实完成范围、未确认项、最小补拍需求及下一步。

最终分别报告四种状态：结构静态检查、外观对账、导出与页面验证、实物复拼。没有用户实物复拼证据，最后一项必须为“未验证”。灯笼无机关时写“不适用”，不为展示效果虚构关节。不要把剩余不确定项藏在“整体已完成”里。

立即接续当前进度并分派只读审计；不要先询问是否开始，也不要要求用户重复上传已有六张照片。
